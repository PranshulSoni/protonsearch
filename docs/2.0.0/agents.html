06 / AGENT RUNTIME

Many agents. Explicit authority.

Search finds things. Agents take actions through a visible, controlled execution system.

Interaction flow

  1. User types a query in Search. Results stay results; pressing Enter preserves current open behavior.
  2. User explicitly selects “Run with agent” or opens Agents, chooses a provider and sends a task.
  3. Runner creates a durable job, displays planned tools and scope, and requests any required grant.
  4. Agent executes through the broker, streams progress and pauses for approvals. User can stop a job or all jobs.
  5. Completion shows outputs, changed resources, failures and an activity record with a deliberate retention policy.

Separate concepts

Local runtime

Scheduler, history and tool broker run on the PC.

Model provider

Local model via an installed runtime or remote API; clearly label where prompts are sent.

Execution boundary

Tools enforce grants independently of model instructions. A process boundary alone does not restrict filesystem access.

Job state contract

queued → starting → running ↔ awaiting_approval
                     ↓                  ↓
             cancelling → cancelled    denied
                     ↓
              succeeded / failed / interrupted

Persist run ID, agent/provider ID, originating profile, task scope, timestamps, grants, tool requests, usage budget and output references. Idempotency keys prevent double execution on reconnect. On restart, mark nonterminal runs interrupted and reconcile provider state; never automatically replay writes.

Scheduler proposal

  • Two concurrent jobs by default, configurable within measured CPU/memory/provider limits. Queue additional jobs fairly.
  • One computer-use lease per desktop session; it pauses when the user resumes input and never drives secure desktop/UAC.
  • Resource locks for shared write targets; independent read-only tasks may run concurrently.
  • Deadlines, token/cost ceilings and output caps per run. Child process trees tracked with Windows Job Objects where applicable.
  • Pause on lock and suspend where required; approvals expire. Profile switches never confer additional authority or silently terminate a job.

Capability policy

Tool classDefaultScope
Search metadataAllowed after feature consentQuery limits and selected sources; content sensitivity policy
Read fileScoped folder/selection grantCanonical paths, symlink/reparse handling, size cap; handle-based checks where possible
Write/move/deletePreview and per-action or bounded run approvalExact targets, operation, expiry and revocation
Shell executionDisabled for untrusted widgetsExplicit executable/argument scope; arbitrary shell is broad same-user authority

Network/send/publishSpecific destination and payload approvalNo silent upload of indexed content or secrets
SecretsUnavailable to model/widgetProvider-scoped broker lookup; redacted logs

Prompt injection in files, search results or web content is data, never authority. A grant is checked at execution time, bound to authenticated caller/run/tool/resource, and revocable. Global “always approve” cannot be inherited from 1.x. Keep profile appearance and security grants independent.

Reuse and repair

The existing ai.rs streaming callbacks are a useful adapter seam. Hermes remains one provider, not the entire job scheduler. Before exposing concurrent agents: replace fixed gateway-key fallback, remove credentials from command-line arguments, isolate global approval state, and separate chat UI from job persistence. The present integration enables terminal/computer-use/code-execution tools; wrapping it in a new panel is insufficient. See repository audit.

Containment truth

Brokered tools are enforceable when the worker lacks independent access to the same resource. An arbitrary native CLI running as the user can bypass application checks; label it trusted full-user execution, or implement and verify an OS restriction such as a tested AppContainer configuration. Windows Job Objects help lifecycle/resource control, not complete filesystem isolation. Restricted tokens/AppContainer design is a separate spike before claiming a sandbox. [S15]

Security acceptance

  • Cross-run approval IDs cannot authorize another run; expired/modified actions require fresh approval.
  • A malicious widget cannot call broker operations outside its grants, spoof another instance or access secret storage.
  • Stop cancels queued work, streams and owned child processes; providers report cancellation limits honestly.
  • Restart never silently repeats a completed external action.
  • Tests include injection attempts, forged IPC origin, path traversal/reparse points, oversized outputs and stalled tools.

Agent settings must distinguish local model availability, remote provider credentials, offline state, model resource use and possible usage costs. Running multiple local agents does not require shipping a model or a cloud account with the dock.

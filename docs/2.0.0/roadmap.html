Suggested staffing: one Rust/Windows engineer and one UI engineer, with focused QA and security review at gates. For a solo maintainer, keep the same sequence and reduce parallel work. Calendar estimates are intentionally deferred until Stage 1 measures platform risk; hundreds of widgets are not a credible first-release estimate.

The first ten working days · suggested investigation budget

  1. Days 1–2: Freeze baseline, run existing tests on Windows, create anonymized fixtures, specify preview data identity and backup strategy.
  2. Days 3–4: AppBar stub, work-area negotiation, two monitors, DPI/fullscreen and deterministic exit restore; no taskbar hiding initially.
  3. Days 5–6: Identical Slint and Tauri sample docks; collect process-tree memory, input/frame latency and accessibility evidence.
  4. Days 7–8: Window identity/activation and native tray access; crash/watchdog proof for any candidate hide adapter.
  5. Days 9–10: Document results, choose renderer, reduce unsupported features, refine estimates and prepare first service extraction.

This is a timebox proposal, not a promise that Windows compatibility can be solved in ten days. Failed gates produce an explicit fallback or narrower support claim.

Release verification matrix

  • Windows 11 serviced builds selected at kickoff; x64 integrated GPU laptop and desktop; ARM64 later unless dependencies and native matrix pass.
  • One/two/three monitors, mixed 100–200% DPI, portrait, negative coordinates, hotplug, primary display switch.
  • Fullscreen games/video, sleep/resume, lock/unlock, RDP, Explorer restart, elevated app activation, IME and keyboard shortcuts.
  • Narrator, keyboard-only reorder/resize, high contrast, text scaling, reduced motion and right-to-left layout.
  • Fresh install, side-by-side v1/preview, migration retry, corrupt DB, low disk, offline network, downgrade and uninstall preserve-data behavior.
  • Agent/job crash, expired grants, provider timeout, widget crash/resource exhaustion, update rollback and standalone recovery.

Definition of release readiness

Every committed feature has a documented owner and test. Search parity, restore behavior, user-data preservation and accessibility are hard gates. Unsupported complete-tray hosting or notification mirroring is omitted from stable claims. If replacement mode fails, ship coexistence only with clear product wording; do not hide a failed requirement behind a demo.

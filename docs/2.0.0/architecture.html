This diagram is a target architecture. Begin with modular Rust code and only the process boundaries needed for UI responsiveness and recovery; introduce the widget worker when third-party execution arrives. No microservices, HTTP server, cloud account or service-install elevation is required.

Search request path

  1. UI sends SearchRequest { generation, query, scope, limit } after existing debounce behavior.
  2. Search service parses prefixes and consults cached app/file metadata first. Emit a fast batch tagged with generation.
  3. Content/OCR and other slow providers run behind bounded work queues. Emit ranked incremental batches only while the request remains current.
  4. UI discards stale generations. Selected result resolves to a typed action through the broker, preserving v1 behavior through a legacy adapter during extraction.

System state path

Windows events → platform snapshot → coalesced subscription → affected widget view. A single audio subscription feeds every audio widget; each widget does not independently poll COM. Pause visual updates when hidden and reduce background activity on battery saver. Weather fetches use a bounded cache and explicit refresh policy.

IPC proposal

Use local Windows named pipes with a current-user/session restricted DACL, explicit caller identity checks and protocol handshake. Never use a fixed localhost key as authorization. Version envelopes; start with bounded length-prefixed JSON, maximum 1 MiB per message, and separate attachment references. This is a design proposal, not a property of named pipes automatically. [S14]

{
  "protocol": 1, "request_id": "r-42", "generation": 17,
  "origin": {"kind": "widget", "instance_id": "weather-work"},
  "method": "weather.refresh",
  "params": {"location_ref": "city-pune"},
  "deadline_ms": 2000
}

The server derives authenticated caller identity and grants from the connection; it never trusts the origin JSON as proof. Responses carry request ID, result/error and revision. Events have sequence numbers and a snapshot-resync path. Queue overflow coalesces replaceable state; approvals and job transitions are durable. Reject oversized messages, duplicate actions and incompatible major protocol versions.

Persistence

  • Preview identity: separate %LOCALAPPDATA%\ProtonPreview\2; import from existing %APPDATA%\protonsearch explicitly.
  • Personal state: profiles, widget configuration, notes, pins and agent runs in a versioned SQLite database; secrets remain in Windows credential storage.
  • Rebuildable state: index metadata/FTS and thumbnails in separate local files; no migration rollback depends on preserving a new index.
  • One logical writer per database: short transactions, WAL policy, busy timeout and consistent backups; no shared UI-thread connection.
  • OS state: recovery journal saved before taskbar mutation and restored independently of profile/database health.

Concurrency and failure

UI and Win32 message dispatch stay on their owning thread. COM providers have explicit apartment affinity and marshal data rather than passing interface pointers arbitrarily. A bounded executor handles network I/O; capped blocking pools handle filesystem, extraction and SQLite. Keep existing extraction child timeout. Search outage produces a retry state; agent outage preserves jobs; widget failure produces an error tile. None may hang dock input.

First extraction seam

Create protonsearch/src/domain.rs, storage.rs, search_service.rs and platform/ inside the existing crate before moving to the proposed workspace. Adapt old main.rs to consume these services. New directories and crates shown here are planned, not created.
